# 自主无人机项目：开源方案选型与反证审查

- 日期：2026-09-28
- 状态：候选选型与集成验证计划；不是板端性能、闭环或实飞通过结论。
- 配套需求：[最新需求与开发收敛条件](./自主无人机项目_最新需求与开发收敛条件_2026-09-28.md)。本文沿用 REQ-01～REQ-14。
- 用户要求：按需求有选择地参考开源方案，反复审查；独立判断用户指令中的假设和冲突，不将指令自动视为正确的技术结论。
- 审查范围：官方仓库、官方文档、若干核心源文件及本地已取得的网球项目源码。未安装候选运行环境、未执行 RK3588 基准、未修改无人机产品仓库、未操作飞控。

## 1. 决策摘要

**采用模块化候选组合，不整体移植任意一个开源项目。先证明输入输出和失效边界，再决定生产依赖。**

| 模块 | 当前选择 | 选择性质 | 对应需求 |
|---|---|---|---|
| RK3588 人体关键点 | Rockchip RKNN Model Zoo 的 YOLOv8n-Pose 示例作为优先验证起点 | 条件性推荐；不是无需修改的生产组件 | REQ-01、03、13 |
| 姿态备选 | RTMPose + 人体检测器 | 保留正式替代路线，不能说其无 RKNN 支持 | REQ-01、03、13 |
| 短时框关联 | ByteTrack | 性能与身份关联的比较基线，不作为最终身份保证 | REQ-01、09 |
| 移动相机与遮挡关联 | BoT-SORT 的运动、外观关联及相机运动补偿 | 优先对比候选；ReID 模型和 RKNN 部署需另行验证 | REQ-01、04、09 |
| 有尺度三维骨架 | OpenCV 标定、校正、三角化 | 几何方法基线；必须增加左右身份匹配和有效性检查 | REQ-04、13 |
| 环境深度 | OpenCV StereoSGBM | 可解释的实验比较项，不单独承担安全放行 | REQ-08 |
| 局部规划 | 先审查现有模块；EGO-Swarm 系列作算法与接口比较对象 | 不批准直接替换项目架构 | REQ-05、06、08 |
| 降落区域判断 | 独立感知与决策工作包 | 尚无满足本项目条件的现成方案被批准采用 | REQ-11、12 |
| 网球项目 | 保留少量 RKNN 与应用组织方式的参考 | 不整体移植，不作为无人机主工程 | 主要为部署学习 |

所有候选需要通过第 7 节门槛后，才能升级为项目正式选型。无已确认阈值或证据时保持“未验证”，不能给出“选择必然正确”的承诺。

## 3. 逐项选择与排除理由

### 3.1 RK3588-Tennis-Correction-Sys：只作局部参考

复查文件为 `tennis_lib/pose_detector.py`、`common.py`、`camera_openni.py`、`gui/app.py` 及转换脚本。[项目快照](https://github.com/wycyhwgmx/RK3588-Tennis-Correction-Sys/tree/bbba4ae2b506580a49a9b8a171563c06870e0ac5)

适合学习模型调用和预后处理组织方式。不复用网球动作评分、报告、GUI 作为飞行主链，也不把深度采集接口当三维骨架融合实现。

源码层面的集成障碍：

1. `RknnResult` 对外主要提供关键点；跟踪器需要的人体框、检测分数和关键点关联必须重新定义，不能直接接入。
2. 核心评分逐帧选择人物，没有持续指定身份管理。
3. 网页加载 `.pt`，命令行走 RKNN；当前检测器显式选择一个 NPU 核，不能沿用介绍中的三核和帧率作为性能证据。
4. 多种后处理分支具有特定输出结构假设，不能把任意同名 YOLOv8-Pose 文件替换进去。

结论：不作为生产基线；若提取代码，逐段与官方输出对照并保留来源。

### 3.2 Rockchip YOLOv8n-Pose：优先做部署和输出一致性验证

官方示例明确列出 RK3588，并提供转换与推理路径。[示例说明](https://github.com/airockchip/rknn_model_zoo/blob/main/examples/yolov8_pose/README.md)

推荐原因是平台适配证据直接、同时输出人体框和关键点；不是已经证明其在本项目精度或速度最优。

本次读取 Python 示例发现：检测阈值为 0.5；输出处理针对特定的四输出结构；关键点坐标在处理中存在整数截断。转换脚本含图节点名称相关的混合量化配置。它们是示例实现约束，不能无审查复制进三角化和跟踪管线。[推理源文件](https://raw.githubusercontent.com/airockchip/rknn_model_zoo/main/examples/yolov8_pose/python/yolov8_pose.py)、[转换源文件](https://raw.githubusercontent.com/airockchip/rknn_model_zoo/main/examples/yolov8_pose/python/convert.py)

集成要求：保留浮点坐标；验证缩放补边与颜色归一化；保留跟踪需要的低分候选；分别定义人体检测分数和关节置信度。普通 Ultralytics 导出和 Rockchip 适配导出的后处理不得混用。C 示例当前说明只支持 8 位量化，应按最终选择的运行路径验证。

### 3.3 RTMPose：正式备选，不因“不是 YOLO”排除

RTMPose 官方材料提供 RKNN 配置；对应配置包含静态输入和 SimCC 输出，并关闭量化。因此“RTMPose 没有 RKNN 路线”是不成立的。[官方说明](https://github.com/open-mmlab/mmpose/tree/main/projects/rtmpose)、[MMDeploy RKNN 配置](https://raw.githubusercontent.com/open-mmlab/mmdeploy/main/configs/mmpose/pose-detection_simcc_rknn-fp16_static-256x192.py)

它通常需要人体检测、裁剪及关键点推理的衔接。需要计入所有候选人物、左右视图、裁剪恢复的整体成本，而非只比较姿态网络延迟。

触发比较的条件：优先方案在坐姿、上半身遮挡、关键点稳定性或许可证约束上不合适，或已有项目实现已经使用 RTMPose。不能为统一名称而推倒可验证的已有实现。

本次未确认具体权重、目标 SDK 的转换成功率及 RK3588 实测性能，保留未验证状态。

### 3.4 ByteTrack：关联基线，不等于持续指定身份

ByteTrack 使用高低置信度检测进行关联，原始实现按更新次数推进轨迹并以帧数管理丢失期限。[项目](https://github.com/FoundationVision/ByteTrack)、[核心实现](https://raw.githubusercontent.com/FoundationVision/ByteTrack/main/yolox/tracker/byte_tracker.py)

它适合检验框关联收益及计算成本，但不能保证完全遮挡后不换人。必须额外定义用户指定目标、失效、候选身份冲突和恢复确认。

关键修正：上游若先按 0.5 丢掉全部低分框，再接 ByteTrack，不能期待原算法的低分关联能力。应联合校准检测、NMS、轨迹关联阈值，并保持低分框只能在合适条件下支持关联，不能自动转化为可信飞行观测。

可变帧率、丢帧和降频运行时，要核对实际时间间隔与运动模型；不能将 `track_buffer` 的帧数直接宣称为固定秒数。

独立审查新增发现：原版 `BYTETracker.update` 内部再次按输入尺寸对框做缩放。上游已经还原到原图坐标时，适配错误会造成重复缩放；该函数还可能就地修改传入数组。需明确唯一坐标还原责任，保留不可变观测或隔离缓冲区，并用不同宽高比、裁剪和分辨率样例验证框与关键点保持对应。

### 3.5 BoT-SORT：多人交叉的优先比较项，但不是身份认证

原项目提供运动、外观及相机运动补偿，适合纳入移动相机场景比较。[原项目](https://github.com/NirAharon/BoT-SORT)、[核心实现](https://raw.githubusercontent.com/NirAharon/BoT-SORT/main/tracker/mc_bot_sort.py)

但不同实现的默认配置不同。例如本次读取的 Ultralytics `botsort.yaml` 中 `with_reid: False`，不能只写“使用 BoT-SORT”就声称启用了外观重识别。[配置来源](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/cfg/trackers/botsort.yaml)

需记录具体实现、是否启用 ReID、权重来源、特征维度、裁剪和归一化、匹配阈值，以及 RKNN 转换结果。不能默认 RKNN 姿态结果具有框架 `model:auto` 所需的内部特征接口。

ReID 会受相似服装、转身、局部遮挡和错误模板更新影响。图像运动补偿也不等于三维自运动估计；近景视差、相机平移时要检查补偿是否失效。原算法参数不能直接充当飞行置信门槛。

### 3.6 OpenCV 三角化：米制数据基线，保留误差与缺测语义

采用内外参标定、畸变处理、校正及三角化的几何路径。必须先完成左右人物身份和同名关节匹配；两个单目跟踪器生成相同数值 ID，并不代表同一个人。[官方几何接口](https://docs.opencv.org/4.13.0/d9/d0c/group__calib3d.html)

基线单位、同步误差、图像坐标还原、正深度、极线约束及重投影残差应进入有效性检查。神经网络为遮挡部位输出的坐标不自动成为真实观测。不能通过填零凑齐骨架后继续三角化。

根相对骨架、相机坐标骨架和导航坐标轨迹分别标明。三维数据精度暂不作为展示门槛，不取消跟飞躯干距离的异常检测。

### 3.7 MediaPipe／单目三维：不作为相机到人体距离的替代

MediaPipe 文档的 world landmarks 是以髋部中点为原点的米制三维输出。它不直接提供相机到人体的绝对平移；不能因为字段叫 world 就将其直接用于三米距离控制。[官方坐标定义](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/python)

不纳入当前米制距离主链；可在以后作为离线姿态比较项。该判断针对测距需求，不是否认其姿态能力，也不声称所有单目方案均不可能借助外部约束获得尺度。

### 3.8 环境深度与规划：先检查传感器输入，再选择规划器

OpenCV StereoSGBM 可以作为传统视差实验基线，但其输出不是占据地图，更不是安全通行许可。低纹理、反光、遮挡及不同步时应保留无效深度和未知空间，不能用“未检测到障碍”替代“已观测可通行”。[StereoSGBM 文档](https://docs.opencv.org/4.13.0/d2/d85/classcv_1_1StereoSGBM.html)

EGO-Planner 官方页指向 EGO-Swarm 后续实现，并提供 ROS2 分支信息。仅将其列为局部规划方法与接口比较对象；不能将多机避碰能力等同于动态行人避碰，也不能默认带人体身份或骨架可见性目标。[EGO-Planner](https://github.com/ZJU-FAST-Lab/ego-planner)、[EGO-Swarm](https://github.com/ZJU-FAST-Lab/ego-planner-swarm)

选择之前核对：里程计、环境深度/点云及地图输入、飞行包络、未知空间策略、失效行为、ROS/飞控接口版本及 RK3588 负载。项目已有规划模块优先审查，不先整体迁移 ROS 栈。

路径检查需要覆盖整机体积、安全余量、制动空间和局部空间信息的时效，不能仅检查中心线。PX4 的 Collision Prevention 与伴随计算机自主绕行也不能混为一谈；本次查看 v1.16 文档，其功能与模式边界须与实际固件匹配，不能假定 Offboard 指令会自动获得同等保护。[PX4 v1.16 Collision Prevention](https://docs.px4.io/v1.16/en/computer_vision/collision_prevention)

旧 PX4-Avoidance 已于 2024-08-01 归档，页面明确未维护。它的 safe_landing_planner 可用于理解历史模块划分，不能作为新项目即插即用的现行避障与降落组件。[归档项目](https://github.com/PX4/PX4-Avoidance)、[历史降落模块](https://github.com/PX4/PX4-Avoidance/tree/master/safe_landing_planner)

## 4. 对用户指令和既有建议的独立审查

本节是工程判断和建议修订，保留原目标；不伪称用户已批准这些新增边界。

| 原表述 | 独立判断 | 建议落实方式 |
|---|---|---|
| 暂不考虑数据误差 | 对骨架展示精度可以成立，对跟飞测距与状态有效性不成立 | 分开设置采集精度目标与控制输入有效性门槛 |
| 头肩躯干可见即可持续跟随 | 只能证明图像有部分人体，不能证明双目深度、身份、路径都有效 | 将其作为采集退化条件；飞行继续还需独立通过其他门槛 |
| 要始终不跟错人 | 可以作为指定测试中的硬失败条件，不能宣称开放环境零误认 | 增加拒绝重新锁定和人工确认出口；报告误跟与不必要拒绝 |
| 有安全更好视角就主动寻找 | 目标合理，但系统不具备全知环境信息 | 定义在有限已观测可达空间内搜索；未发现路径不等于证明不存在 |
| 丢失或危险时悬停 | 悬停依赖自身状态估计与空间余量 | 按定位健康、障碍变化和电量决定处置，禁止无期限等待 |
| 无人接管就自动降落 | 不能以超时替代降落区域判断 | 降落许可需独立且持续有效；无安全区域的行为必须闭合 |
| 无云台仍完整观察 | 可作为约束，但飞机姿态与相机朝向耦合 | 用视野、模糊及机动数据验证，不承诺任意动作全身入镜 |
| 反复审查确保选择正确 | 审查能减少错误，不能替代目标硬件与场景验证 | 用来源、反例、独立复核及退出标准表达结论强度 |

建议的独立状态字段包括：目标身份可信、图像采集有效、三维观测有效、骨架可见性、飞机定位健康、路径可通行、降落条件有效。它们不能合并成一个“跟踪置信度”。

## 5. 最小集成接口建议

不同开源模块之间增加薄适配层，避免将某个框架的内部对象传播到全系统。

相机采集到飞控消费的时钟映射必须可核验；机载进程继续发送心跳不证明图像或目标状态新鲜。必须由消费端独立检查有效期，防止生产线程卡死而旧结果被反复发送。[PX4 v1.16 Offboard 参考](https://docs.px4.io/v1.16/en/flight_modes/offboard)；实际固件尚未在本次研究中锁定。

| 输出 | 必需语义 |
|---|---|
| 人体检测 | 帧/视图标识、采集时间与时钟域、人体框、检测分数、浮点关键点、关节置信度和坐标还原信息 |
| 身份跟踪 | 指定目标、轨迹状态、关联证据、最后真实观测时间、是否处于预测、身份模糊标记 |
| 双目测量 | 配对帧、左右目标关联、单位/坐标系、三维关节/躯干、有效掩码、几何检查与质量 |
| 规划输入 | 目标状态及有效期、自身状态、障碍与未知区域、传感器覆盖、运动边界 |
| 数据存档 | 模型/标定/软件版本，观测、预测和缺测分类；不能仅留渲染视频 |

如果姿态检测在局部人体上容易漏检，应实验比较独立人体检测器是否有收益，而不是先叠加第二个模型增加负担。两路相机、ReID、深度、规划、编码的总资源成本需统一预算。

## 6. 许可证与依赖边界

本节记录已查看的许可证标识与待核查事项，不构成对具体产品使用方式的法律结论。

- 网球项目、原始 ByteTrack、原始 BoT-SORT 页面分别标示 MIT；不能因此推定其全部模型和依赖都按 MIT 授权。
- RKNN Model Zoo 标示 Apache-2.0，但它引用的 Rockchip Ultralytics YOLOv8 源码含 AGPL-3.0 许可证。包装层许可证不能覆盖底层来源。[上游许可](https://github.com/airockchip/ultralytics_yolov8/blob/main/LICENSE)
- MMPose 主仓库为 Apache-2.0；模型、数据来源和部署依赖仍需分别登记。[MMPose LICENSE](https://github.com/open-mmlab/mmpose/blob/main/LICENSE)
- 原始 BoT-SORT 与 Ultralytics 内的同名实现不是同一授权对象。读取的 Ultralytics 配置标注 AGPL-3.0，原项目内 fast_reid 另有 Apache-2.0 文件。
- EGO 系列仓库标示 GPL-3.0；是否复制、修改或作为进程集成，应结合实际交付方式审查。

选定具体文件与权重后建立清单：来源、commit/hash、许可证、修改范围、分发方式及通知文件。发现不适合预期交付方式时，可切换备选，而不是以“开源”作为自动许可。

## 7. 验证门槛与反例测试

所有数值门槛需先从现有有效需求获取，缺失则提出待确认值；不能看完结果后降低标准。

| 门槛 | 必做比较／反例 | 否决或保留未验证的条件 |
|---|---|---|
| G0 来源与版本 | 固定 commit、模型哈希、许可证、SDK/驱动、标定 | 无法复现或授权来源不清，不能进入正式依赖 |
| G1 模型等价性 | 相同图像对照原模型、ONNX、RKNN；检查框、分数、关键点 | 后处理契约不一致、坐标错误、重要场景退化未解释 |
| G2 指定身份 | 同衣交叉、转身、坐起、桌后上半身、出入画、长遮挡、变帧率 | 在身份不确定时错误输出“可继续跟随” |
| G3 双目有效性 | 左右串人、不同步、零/小视差、遮挡关节、边缘与反光 | 无效数据被标为可信距离或米制骨架 |
| G4 完整负载 | 两路采集+姿态+候选ReID+深度+规划+录像；记录尾延迟、队列、丢帧、温度和内存 | 只提供单模型 FPS；冻结图像或过期预测仍被当新观测 |
| G5 环境与观察 | 纹理少的隔断、细腿、侧后盲区、无可达好视角、站坐切换 | 未知空间被当空闲；来回追逐视角；越界搜索 |
| G6 降落区域 | 空区域、桌面/边缘、有人进入、区域不可见、状态过期 | 仅测高或检测不到人就批准降落 |
| G7 闭环 | 回放→真实动力学仿真→受控验证；注入定位退化、超时、恢复跳变 | 将离线逻辑通过宣称实飞通过；异常链不闭合 |

比较 A：同一检测输入下对比 ByteTrack、BoT-SORT 无 ReID、BoT-SORT 有 ReID，分离关联与外观收益；另做端到端负载测试。

比较 B：YOLOv8n-Pose 与检测器+RTMPose 使用相同场景、明确输入分辨率及完整管线成本。不能只比较不同论文的 FPS 或 mAP。

数据按录制场次和人员划分调参与保留测试集，避免同一片段不同帧泄漏。记录误跟、错误重捕获、拒绝率、恢复时间、有效深度比例及连续采集情况；展示精度不考核不等于不记录数据质量。
